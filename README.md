# AI-помощник для товарных описаний

Прототип сервиса: получает данные о контрольно-измерительном приборе и через OpenAI API готовит черновик карточки для B2B-магазина. Результат: SEO-заголовок, SEO-описание, таблица характеристик, поисковые запросы и блок для менеджера. Работает через веб-форму и JSON API.

## Запуск

Нужны Python 3.12+ и ключ OpenAI API.

```bash
git clone https://github.com/vladick5513/product-description-ai.git
cd product-description-ai
python -m venv .venv
.venv\Scripts\activate            # Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
copy .env.example .env            # Linux/macOS: cp .env.example .env
```

Впишите ключ в `.env`, в поле `OPENAI_API_KEY`. Файл `.env` добавлен в `.gitignore`. Затем запустите сервис:

```bash
uvicorn app.main:app --reload
```

- Форма: http://localhost:8000/
- Документация API: http://localhost:8000/docs

Запрос через API:

```bash
curl -X POST http://localhost:8000/cards -H "Content-Type: application/json" --data-binary @samples/rgk_ct_12.json
```

Модель задаётся в `.env`, поле `LLM_MODEL`. Модель должна поддерживать Structured Outputs.

## Вход и выход

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": {"диапазон измерений": "0–1,6 МПа", "класс точности": "1,5"},
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

Обязательно поле `name` и хотя бы одно из полей `specs` и `description`.

| Поле ответа | Что содержит |
|---|---|
| `status` | `ready` или `needs_review`, если есть пропуски, вопросы или непройденные проверки |
| `card` | `seo_title`, `seo_description`, `key_characteristics`, `search_queries`, `commercial_block`, `clarifications` |
| `missing_fields` | какие поля отсутствуют во входных данных или пусты |
| `warnings` | что не прошло автоматическую проверку после всех попыток |
| `seo_title_length`, `seo_description_length` | длина текстов в символах |
| `markdown` | карточка в Markdown для копирования |

| Код | Когда возвращается |
|---|---|
| 422 | некорректный JSON, пустое `name`, неизвестное поле или нет ни характеристик, ни описания. Запрос к LLM не отправляется |
| 502 | ключ отклонён, ошибка API, отказ модели или ответ не по схеме |
| 503 | превышен лимит, закончились средства на счёте API или нет связи с API |

Входные данные лежат в `samples/`, результаты работы сервиса в `examples/` (модель `gpt-6.1-sol`, тексты не правились вручную). Обновить результаты можно одной командой (нужен ключ в `.env`, запросы платные):

Строки таблицы характеристик PRT-101, у которых на сайте нет понятного названия, в пример не вошли. Таблица зондов RGK CT-12 приведена в сокращённом виде.

## Промпт

Промпт находится в `app/card/prompts.py`. Основные приёмы:

- **Один источник фактов.** Данные передаются в теге `<product_data>` и объявлены данными, а не инструкциями. Это снижает риск, что модель выполнит инструкции из текста описания.
- **Факты важнее объёма.** Модель прямо предупреждена, что нельзя добавлять характеристики ради длины текста.
- **Разобранные ловушки.** Запрещены пересчёт единиц, дописывание единиц к голым числам, перенос цены и рекламы, а также собственные выводы о совместимости, пригодности и новых сферах применения. Описание нескольких серий нужно фильтровать по этому товару.
- **«Данных нет» в таблице.** Модель добавляет 3–5 важных для такого прибора характеристик, которых нет во входных данных. Менеджер сразу видит, что стоит запросить.
- **Запас по длине.** Модель просят написать 900–1100 символов, а проверка допускает 800–1200.

## Решения

**Модель не считается надёжной, ответ проверяется кодом** (`app/card/validation.py`). Проверки такие:

- длина заголовка и описания, число запросов;
- значение характеристики совпадает с входным, если такая характеристика есть в `specs`; иначе его числа и слова должны быть подтверждены входными данными с точностью до падежа, либо значение должно быть равно «данных нет»;
- в текстах нет чисел и латинских терминов, которых нет на входе. Так ловятся `Modbus` и пересчёт МПа в бары;
- в текстах нет утверждений из короткого списка (гарантия, сертификат, поверка, ГОСТ, взрывозащита и другие), если их нет на входе.

**Ошибки возвращаются модели.** Список проблем уходит ей на исправление, всего до 3 попыток. Если чисто не получилось, сервис отдаёт лучший вариант со статусом `needs_review` и списком `warnings`: черновик с указанными проблемами полезнее ошибки.

**Пропуски определяет код, а не модель.** Пустые поля всегда попадают в `missing_fields` и в таблицу со значением «данных нет», даже если модель о них забудет.

**Структурированный вывод.** Схема ответа задаётся через Pydantic и Structured Outputs. Markdown собирается кодом из JSON, поэтому формат не зависит от модели.

**Структура.** По заданию база данных не нужна, поэтому в проекте нет PostgreSQL, Alembic, DAO и Docker. Код разбит на модуль `card` для карточек и модуль `llm` для внешнего API со своими исключениями.

## Ограничения

- Проверка фактов эвристическая. Она не поймает выдуманное свойство обычными русскими словами вне списка, например «устойчив к вибрации». Вычитка человеком обязательна.
- Число считается подтверждённым, если оно есть где угодно во входных данных, даже в другом контексте. Проверка привязки числа к параметру есть только в таблице, и только для полей из `specs`.
- Значения не из `specs` сверяются по числам и началу слов, чтобы допускать смену падежа. Слово с тем же началом и другим смыслом пройдёт проверку.
- Модель может написать вывод из характеристик без чисел и терминов, например о совместимости или пригодности. Промпт это запрещает, но код такое не ловит, а один запуск не гарантирует того же результата на следующем.
- Если реклама из входного описания содержит гарантию или цену, проверка их не поймает, защищает только правило в промпте.
- Если во входных данных нет описания, SEO-описание может быть короче 800 символов. Это осознанное отступление от объёма в пользу запрета на выдумки: сервис отмечает такой текст в `warnings` и не просит модель его удлинять.
- Форма обрабатывает один товар за запрос, история не хранится.
- Сообщения стандартной валидации FastAPI (например, `Field required`) выводятся на английском.

## Что можно улучшить

- Импорт напрямую из YML-фида и парсинг страниц с характеристиками, пакетная обработка каталога.
- Вторая модель-проверяющая для поиска выдуманных свойств в тексте.
- Набор эталонных товаров и автоматическая оценка качества при изменении промпта.
- Ссылка на источник для каждого утверждения, чтобы менеджеру было быстрее проверять.
- Настройка списка важных характеристик под категории каталога.
